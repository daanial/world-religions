# Localization — architecture and content index

Status: **the technical scaffolding is built and verified working end-to-end** for an arbitrary number of languages (routing, RTL, a scaling language switcher, hreflang/SEO, per-tradition content loading, script-aware fonts). Only one language is actually registered and reachable today: Persian (`fa`). Persian translation is in active phases: shared chrome and several major pages are translated, and six religion modules contain Persian content. A fidelity audit found that some long-form passages are condensed rather than fully translated, so those modules should not be considered final until sentence-level review is complete. The permanent no-condensing rule is in [`translation-rules.md`](./translation-rules.md); see [`i18n-audit.md`](./i18n-audit.md). TTS/narration is intentionally parked and out of scope.

**Read this whole doc before touching code.** Two different AI sessions have worked on this independently and landed two different (both working, both fine) patterns for page-level translation — see "Two patterns in use" below. Pick one deliberately for new work rather than adding a third.

If you're here to translate Persian specifically, read this doc first for the architecture, the status table, and the full content index below, then see [`i18n-persian.md`](./i18n-persian.md) for Persian-specific tone/register/terminology guidance. If you're adding a *new* language, this doc is the whole story — jump to "Adding a language."

## Two patterns in use — pick one for new work

**Pattern A — centralized dictionary** (`src/lib/i18n.ts`): one `UiStrings` interface, one `en` object, one `fa` object, consumed via `useT()`. Used for nav/footer/404/loading and for Concepts' page chrome. Pro: one file to scan for what's translated; keys are reusable across pages (e.g. a shared "Explore" button label). Con: the dictionary file grows to hold every page's strings, and a key name has to be globally unique and self-describing out of context (`conceptsNoneTagged`, not just `noneTagged`).

**Pattern B — page-local `TRANSLATIONS` object**: a `{ en: {...}, fa: {...} }` const declared at the top of the page file itself, e.g. `src/pages/Traditions.tsx`. Pro: everything for a page lives in one file, no cross-file key coordination, easier for a translator working one page at a time. Con: no reuse across pages (each page redeclares "Search" if it needs it), and there's no single file to scan for overall UI-string status — you have to check each page individually (which is exactly why the status table above exists).

**Neither is wrong.** Both were built by a competent hand, both work, both are wired to the same `useLocale()`/`LOCALE_REGISTRY` foundation. Don't refactor one into the other as a side effect of translating a page — that's a bigger, separate decision for the site owner to make deliberately. When translating a page that has neither yet, default to **Pattern A** (the centralized dictionary) for consistency with the majority of what's done so far, unless the page's string count is large enough that a self-contained file (Pattern B) is clearly more maintainable — Traditions.tsx's ~30 keys was a reasonable case for that.

## Architecture in one paragraph

Every language is one entry in `LOCALE_REGISTRY` (`src/lib/locale.ts`) — `{ code, englishName, nativeName, rtl }`. English (`en`) is unprefixed in URLs; every other language is prefixed with its code (`/fa/...`, `/ar/...`). `src/App.tsx` strips that prefix before matching routes (so `/fa/timeline` and `/timeline` render the same route tree) and syncs `<html lang>`/`dir` to the active locale. The nav's language switcher (`src/components/NavBar.tsx`) is a dropdown driven entirely by `LOCALE_REGISTRY`, so it already scales to however many languages you register — nothing UI-side needs to change to go from 2 to 6. Short, structural UI copy (nav, footer, buttons, empty states) lives in a typed dictionary at `src/lib/i18n.ts`. Long-form content — the 44 religion articles — lives in per-tradition files under `src/data/religion-articles/<locale>/`, one file per tradition, generated by `scripts/scaffold-locale-articles.ts` and mirroring the English source's exact shape.

## Adding a language

1. **Register it** in `LOCALE_REGISTRY` (`src/lib/locale.ts`):
   ```ts
   { code: "ar", englishName: "Arabic", nativeName: "العربية", rtl: true },
   ```
   That's it for routing, the language switcher, and hreflang generation — all three read this list directly, nothing else needs code changes to pick up the new entry.
2. **Scaffold its article stubs**: `npx tsx scripts/scaffold-locale-articles.ts ar` — creates `src/data/religion-articles/ar/<id>.ts` for all 44 traditions plus the index.
3. **Wire the loader**: `src/data/religion-articles/index.ts`'s `getReligionArticle()` currently special-cases `fa`. Add an `else if (locale === "ar") return ARTICLES_AR[id] ?? ARTICLES[id] ?? null;` branch (import `ARTICLES_AR` from `./ar/articles`), or generalize it to a `Record<LocaleCode, Record<string, ReligionArticle>>` lookup if you're adding several languages at once — either is fine, just keep the "fall back to English if untranslated" behavior.
4. **Add its UI dictionary** to `src/lib/i18n.ts`: a new `const ar: UiStrings = {...}` and add it to the `DICTIONARIES` map.
5. **Font, if RTL and not Arabic-script**: `src/styles/rtl.css` currently only covers Arabic-script languages via Estedad, scoped to `html[lang="fa"]`. A new Arabic-script language can extend that same selector (`html[lang="fa"], html[lang="ar"]`). A non-Arabic-script RTL language (Hebrew, etc.) needs its own font and its own selector.
6. **Translate content** per the index above.

Nothing about routing, the switcher UI, or SEO plumbing needs to change for step 6 through 3 languages or 6 — that was the point of building it this way.

## RTL

`html[dir="rtl"]` is set automatically whenever the active locale's registry entry has `rtl: true`. Global layout (nav, footer, containers) relies on **native RTL flex flow** — a `flex-direction: row` container inside `dir="rtl"` already flows right-to-left on its own. **Do not add `flex-direction: row-reverse`** to compensate for anything; doing so double-flips it back to looking LTR. (This was hit and fixed once already during setup — see the comment at the top of `src/styles/rtl.css`.) Fix real RTL issues with logical properties (`margin-inline-start/end`, `text-align: start/end`, `inset-inline-*`), scoped under `html[dir="rtl"] .some-component` in `rtl.css`; don't touch the base LTR stylesheets to do it.

**Font**: Persian (and Arabic-script languages generally) render with [Estedad](https://fonts.google.com/specimen/Estedad), loaded in `index.html` and applied via `src/styles/rtl.css` by overriding the `--font-display`/`--font-body` CSS variables under `html[lang="fa"]` — every component that already does `font-family: var(--font-display)` picks it up automatically, no per-component changes needed. This is scoped to `lang`, not `dir`, specifically because Estedad only covers Persian/Arabic glyphs — a future RTL language in a different script (Hebrew, etc.) would render with tofu/fallback boxes if it inherited this rule, so it needs its own font and its own `html[lang="..."]` block, not a blanket `dir="rtl"` selector.

## Verifying your work

1. `npm run dev`, visit `/<code>/...` for the locale you're working on.
2. Check `document.documentElement.dir` and `lang` (DevTools console) match the registry entry.
3. Use the language switcher (globe icon, top right of the nav) — it should preserve the current page across languages, not bounce to the homepage.
4. `npx tsc -b --noEmit` should stay clean — the whole content system is fully typed, so a malformed `ReligionArticle` literal fails the build rather than silently rendering wrong.
5. For a translated article specifically, load `/<code>/religion/<id>` and confirm it's actually translated, not still the English re-export.

## Known gaps (technical work still outstanding, not translation)

1. **Per-page SEO strings aren't localized on most pages.** `Timeline.tsx`, `Landing.tsx`, `GlobeView.tsx`, `Compare.tsx`, `Pilgrimage.tsx`, `InwardPaths.tsx`, `About.tsx`, `ReligionDetail.tsx` all call `usePageSeo({ title, description, ... })` with hardcoded English strings regardless of locale. (`Concepts.tsx` and `Traditions.tsx` already do this correctly — copy their approach.) Fix per page: add the title/description as keys in `i18n.ts` (or that page's own `TRANSLATIONS` object if using Pattern B) and pass `t(...)`-resolved values into `usePageSeo`.
2. **Dynamic data labels** in GlobeView, Timeline and untranslated religion cards remain English; translate these in dedicated locale datasets as each phase expands.
3. **`GlobeView`, `Timeline`, `Pilgrimage`, `InwardPaths`, `About` don't import `useLocale` at all** — meaning any `<Link>`/`<NavLink>` inside them that doesn't go through `withLocale()` will point to the unprefixed English URL even when the user is on a `/fa/...` page. Check each for internal links when translating, not just visible text — a translated page that then link-jumps you out of `/fa/` back to English is a worse experience than an untranslated page that at least keeps you in `/fa/`.
4. **Sitemap/prerender only emit English routes, by design.** `src/lib/site.ts`'s `getAllRoutes()` and the scripts that consume it (`generate-sitemap.ts`, `prerender.ts`) don't include `/<code>/...` URLs yet. Deliberate: publishing 44 `/fa/religion/*` URLs to search engines while they're still English content under a Persian URL would be duplicate content. Once a language has real (not placeholder) translations, extend `getAllRoutes()` to accept a locale and generate both variants, gated on which ids are actually translated in that locale's `ARTICLES_<CODE>` map.
5. **RTL visual QA for interactive/canvas components hasn't been done**: `GlobeView` (Three.js), `Timeline` (drag/zoom scrubber), `PilgrimGeoMap` (Mapbox), and `About`'s 3D image carousel all position things with JS/canvas math written assuming LTR. Check each on a real `/fa/...` visit once there's translated content to look at.
6. **The six `text-align: left` rules** listed above under RTL.
7. **`getReligionArticle()`'s locale branching is hand-written per-language** (currently just an `if (locale === "fa")`), not registry-driven like routing/switcher/hreflang are. Fine for the current scope; generalize it before adding several more languages.
8. **Two coexisting translation patterns** (see "Two patterns in use" above) — not a bug, but means "is X translated" can't be answered by grepping one file; use the status table and keep it updated.
